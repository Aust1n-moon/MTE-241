=== QUESTION 3 ===
Explain in your own words how the thread’s stack was set up. Comment on what it means to “set up a thread’s stack”, and why we need to store register values on the stack.

The thread starts 0x400 bytes below the initial MSP value which was stored at address 0x0. As a stack grows down, stackptr moves down one slot for the new stack before each write. xPSR (1 << 24) was pushed, then PC as the address of print_continuously, then 14 fillers of 0xA for other registers. The order matters. When the exception returns, the hardware pops xPSR, PC, LR, R12, and R3-R0 in order, then runsFirstThread to pop R4-R11. If the values were pushed in a different order, the wrong values end up in wrong registers, and the PC would never receive the correct function address. Setting up a stack means that the stack is getting filled with fake register values so that it looks like the thread was already running. Register values are stored on a stack because the registers are a thread's entire state. Saving them lets a thread be paused and later loaded back with everything in order to continue. 

=== QUESTION 4 ===
In the switch/case in SVC_Handler_Main, we set PSP using the __set_PSP function before we could run the thread. If we didn’t do this, the code would crash in a hard fault. Explain why

Each thread has its own stack, separate from the main stack where the MSP points to. On the Cortex-M4, PSP is the stack pointer for the threads, while the MSP is used by main. The thread's context was written by the stackptr, not to the MSP stack. runFirstThread reads PSP to pop R4-R11, then returns with LR = 0xFFFFFFFD which tells the CPU to return a thread mode and pop all other registers from PSP. IF __set_PSP was never used, the PSP would hold its default value of 0, instead of pointing to the thread's stack which would make the PC hold meaningless address, causing a Hardfault

When a function returns, it jumps to the address in LR. LR holds address of whoever called the function, but the thread was never called by anything. The CPU will try to execute the code at address 0xA, which is not a valid code location, as it is inside a vector table, holding addresses not instructions.
